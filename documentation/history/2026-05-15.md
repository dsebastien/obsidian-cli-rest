Tests drive `handleRequest` with a minimal `EventEmitter`-based mock req/res pair so they don't need to bind a TCP port and don't trip the `no-restricted-globals` lint rule that forbids `fetch` in plugin code.

## Done (later)

- Fixed issue #2: standard `/Applications/Obsidian.app` installs on macOS weren't auto-detected; only the three Linux-style fallbacks were tried, leaving users to symlink `/Applications/Obsidian.app/Contents/MacOS/Obsidian` to `/usr/local/bin/obsidian` as a workaround.
- Root cause in `deriveCandidatesFromProcess` (`src/app/services/cli-availability-checker.ts`): the asar gate hard-coded `app.asar`, but Obsidian's macOS bundle ships both `app.asar` and `obsidian.asar` in `Contents/Resources/`, and Electron's `argv[1]` can point to either. When `argv[1]` was `obsidian.asar`, the `endsWith('app.asar')` guard failed and no macOS candidate was derived.
- Fix: relaxed the suffix check to `.asar` (or `.asar.unpacked`) and broadened the macOS / Linux / Windows regexes to accept any `*.asar` filename inside the platform's resources directory. The surrounding directory layout (`*.app/Contents/Resources/`, `/usr/lib/obsidian/`, `/opt/<x>/resources/`, `\resources\`) is what actually identifies the install. Renamed the local `appAsar` → `mainAsar` to match.
- Added 4 tests (`src/app/services/cli-availability-checker.spec.ts`) covering `obsidian.asar` argv on macOS, Linux system, Linux `/opt`, and Windows. All 4 fail against the unfixed regex (verified by stash-pop).
