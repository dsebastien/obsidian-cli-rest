## Done (later)

- Fixed issue #1: `/mcp` returned `500 Already connected to a transport` after the first request when concurrent calls overlapped (regression from `@modelcontextprotocol/sdk` 1.26+ which made `Protocol.connect()` throw on a busy `_transport` slot — the GHSA-345p-7cg4-v4c7 fix).
- Refactored `McpServerWrapper` (`src/app/services/mcp-server.ts`) from a singleton `McpServer` shared across requests to the SDK's stateless pattern: each `handleRequest` call constructs a fresh `McpServer` and `WebStandardStreamableHTTPServerTransport`, connects them, handles the request, then closes both. Tool registration moved into `createMcpServer()` and `registerSearchTool` / `registerExecuteTool` now take the new server instance as a parameter.
- `McpServerWrapper.close()` is now a no-op kept only so callers can still treat the wrapper as a closeable resource — there are no long-lived MCP resources to release.
- Added `src/app/services/mcp-server.spec.ts` covering: sequential `initialize` + `tools/list`, ten concurrent `tools/list` calls (which deterministically reproduces the original failure when the singleton is restored), and a `tools/list` snapshot expecting exactly `[execute, search]`. Tests drive `handleRequest` with a minimal `EventEmitter`-based mock req/res pair so they don't need to bind a TCP port and don't trip the `no-restricted-globals` lint rule that forbids `fetch` in plugin code.
