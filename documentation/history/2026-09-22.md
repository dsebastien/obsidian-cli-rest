# 2026-09-22

## Regenerated API keys now apply without a restart

**Problem.** `HttpServerWrapper` captured `apiKey` in its `options` when the server
was constructed. Regenerating the key in settings wrote the new value to disk but
left the running server comparing against the old one, and the UI said so
("Restart server to apply."). The dangerous case is the first key ever set: the
running server still holds `''`, and `validateAuth` treats an empty key as
"auth disabled", so a user who has just generated a key is still serving
unauthenticated requests until they restart Obsidian.

**Fix.** `HttpServerWrapper.updateApiKey(key)` rebinds the value in place, next to
the existing `updateContext` / `setMcpHandler` live-update methods.
`CliRestMcpPlugin.syncServerAuth()` pushes the current setting into a running
server, and the settings tab calls it right after the regenerate write.

**Why not restart the server.** The API key is the one server option the listening
socket does not depend on — unlike `port` and `bindAddress`, which genuinely need
a new socket. `stop()` calls `closeAllConnections()`, so restarting to pick up a
key would drop every in-flight MCP session (`mcp-session-id` state included) and
break any connected agent mid-conversation. Rebinding costs nothing and takes
effect on the next request.

**Coverage.** Two tests in `http-server.spec.ts` drive a real listening server on a
random port and assert against `/api/v1/does-not-exist` (a non-public path, so
auth runs before routing): old key accepted → `updateApiKey` → old key 401s and
the new one passes, server still running; and empty key → unauthenticated request
passes → `updateApiKey` → unauthenticated request 401s. They use `node:http`
rather than `fetch`, which is banned repo-wide by `no-restricted-globals` in
favour of Obsidian's `requestUrl`.

**Verification.** tsc clean, eslint 0 warnings, 207/207 tests, build OK.

**Manual check still needed.** Settings UI is not agent-verifiable: regenerate the
key with the server running and confirm the notice reads "API key regenerated and
applied. Update your clients." and that an old-key client immediately gets 401.

**Related.** The same snapshot bug exists in the OSK plugin
(`obsidian-starter-kit-plugin`), which additionally never restarts on key change
and shows no warning at all. Being fixed separately. The ARD plugin already gets
this right: its `requiresRestart()` excludes the token, so `registry.rebuild()`
rebinds it live.
